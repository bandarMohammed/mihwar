## 1. الهدف والنطاق

نتأكد إن محور يشتغل كما تقول المتطلبات: الموظف يقدم طلب ويتابعه، المدير يعالج طلبات قسمه فقط، الإدارة العليا ترى التحليل والتوصيات، مدير النظام يدير المستخدمين والسجلات، والذكاء الاصطناعي يقترح بدقة مقبولة ومن البيانات المسموحة للدور فقط.

**يغطي:** الخلفية (API) · الواجهات العربية RTL · الصلاحيات · آلية الذكاء الاصطناعي في وصل والعقل التشغيلي واسأل محور.
**لا يغطي (في هذه المرحلة):** اختبارات حمل ضخمة، واختبار اختراق متخصص، وتدريب النماذج (Fine-tuning مؤجل حسب `docs/ai.md`).

## 2. المبادئ

1. **كل معيار قبول في `docs/tasks.md` له اختبار واحد على الأقل**، ونتيجته نجح أو فشل فقط.
2. **اسم الاختبار يبدأ برقم المهمة** (مثل `T-230: …`) عشان نربطه بالـ Pull Request وبالمتطلب.
3. **الصلاحيات تُختبر في الخادم**، وليس بإخفاء الأزرار في الواجهة (NFR-02/03/04).
4. **الإنسان يقرر والذكاء الاصطناعي يقترح:** نختبر إن الحالات الغامضة أو منخفضة الثقة تروح للمراجعة البشرية (Q-07).
5. **لا نخمّن:** أي نتيجة متوقعة ما لها مصدر في المتطلبات أو المستندات تنكتب سؤال مفتوح.

## 5. البيئة وبيانات الاختبار

- **بيئات:** تطوير (لكل مطوّر) · اختبار مشتركة (يُدمج لها الفرع الرئيسي). تحديد الاستضافة والأدوات من المجموعة 3 (Q-04).
- **بيانات تجريبية فقط:** لا نستخدم بيانات موظفين حقيقية. مجموعة بيانات ثابتة: مستخدم لكل دور، قسمين على الأقل (عشان نختبر عزل الأقسام)، طلبات بأولويات وحالات مختلفة، وبيانات شركة (مؤشرات) تتضمن حالات شاذة عمدًا.
- **مجموعة الـ 50 طلب** (من `docs/ai.md`) تُحفظ كما هي ولا تتغير بدون موافقة العضو 3.

## 6. العيوب وكيف نتعامل معها

| الخطورة | التعريف | القاعدة |
|---|---|---|
| حرجة | تسريب بيانات بين الأقسام أو الأدوار · فقدان بيانات · تعطل الدخول | توقف الدمج حتى تنحل |
| عالية | وظيفة أساسية من MVP ما تشتغل · AI يوجّه خطأ بدون مراجعة بشرية | تنحل قبل نهاية المرحلة |
| متوسطة | خطأ في وظيفة ثانوية أو في عرض حالة | تنحل أو تُؤجَّل بقرار القائد |
| منخفضة | تفصيل شكلي | تُسجَّل |

كل عيب يُسجَّل كـ Issue في GitHub برقم المهمة المتأثرة، وخطواته، والنتيجة المتوقعة والفعلية، ولقطة شاشة للواجهة.

## 7. الربط بآلية GitHub

الآلية الكاملة في `docs/tasks.md` (قسم «آلية إدارة الكود»). ما يخص الاختبار منها:

- لا يُدمج Pull Request إلا لما **تنجح الاختبارات والفحوصات** (الأوامر الفعلية تحددها المجموعة 3 في `CLAUDE.md`).
- وصف الـ PR يسرد كل معيار قبول **وكيف تم التحقق منه** (اسم الاختبار أو لقطة شاشة).
- مهام الصلاحيات والذكاء الاصطناعي تحتاج موافقتين (ADR-4001).

## 8. شروط النجاح النهائية

نعتبر الاختبار ناجح ومستعد للإطلاق لما تتحقق **كلها**:

- [ ] كل معيار قبول في `docs/tasks.md` له اختبار ونتيجته نجح.
- [ ] اختبارات الصلاحيات (P-1 → P-12) نجحت 100%، ولا يوجد عيب حرج مفتوح.
- [ ] سيناريوهات التكامل (I-1 → I-8) نجحت للمتطلبات داخل MVP.
- [ ] دقة التصنيف والقسم والأولوية على الـ 50 طلب وصلت الحد المحدد في `docs/ai.md`.
- [ ] كل الحالات الغامضة في المجموعة راحت للمراجعة البشرية.
- [ ] كل توصية فيها مصدر البيانات وتاريخ التحليل وربط بالتشغيلة.
- [ ] كل شاشة اجتازت الحالات الخمس ومراجعة RTL والعربي.
- [ ] لا يوجد عيب عالي مفتوح، وأي عيب متوسط مؤجَّل مكتوب بموافقة القائد.
- [ ] كل Pull Request مدموج مرّ بالمراجعة والفحوصات.
